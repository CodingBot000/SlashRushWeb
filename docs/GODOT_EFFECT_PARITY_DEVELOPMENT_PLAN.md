# SlashRush Godot → Phaser 연출 패리티 복구 개발계획서

작성일: 2026-08-18
기준 원본: `/Users/switch/Downloads/SlashRush-main`
적용 대상: `/Users/switch/Development/Game/WebGame/SLASHRUSH`
문서 상태: 구현 착수 전 승인본

## 1. 목적

현재 Phaser 웹판은 핵심 게임 흐름과 판정 규칙은 동작하지만, Godot 원본에 있던 콤보 팝업, Fever 속도선·버스트, 피격 정지, 보스 파츠 모션 같은 전투 연출이 다수 빠져 있다.

이 계획의 목적은 다음과 같다.

- 원본 리소스와 원본 스크립트를 기준으로 누락된 연출을 복구한다.
- 파일이 없는 문제와 파일은 있지만 연결되지 않은 문제를 구분한다.
- 현재 `GameScene.ts`에 집중된 연출 코드를 독립 모듈로 나눠 이후 조정과 테스트를 쉽게 만든다.
- 데스크톱과 모바일 가로 화면에서 같은 게임 감각을 유지한다.
- 사용자가 명시적으로 보류한 디버그 UI와 보스 메시지 문제는 이번 범위에서 변경하지 않는다.

## 2. 조사 결론과 기준선

### 2.1 리소스 비교 결과

Godot 원본 `assets/`와 Phaser의 `public/assets/godot-source/assets/`를 비교한 결과, `.import`, `.DS_Store`, `.gitkeep`을 제외한 유효 리소스 83개가 모두 보존되어 있으며 파일 내용도 일치한다.

따라서 주요 누락 원인은 리소스 복사 실패가 아니라 다음 세 가지다.

1. Phaser `BootScene`에서 로드하지 않은 리소스
2. 로드했지만 `GameScene`에서 사용하지 않는 리소스
3. Godot에서 코드로 생성하던 절차형 연출을 Phaser에 옮기지 않은 경우

### 2.2 원본 동작 기준

구현 수치와 순서는 다음 원본 파일을 우선 기준으로 삼는다.

- 콤보: `scripts/ui/ComboImpactPopup.gd`
- Fever 화면 연출: `scripts/effects/FeverImpactOverlay.gd`
- 러너 진행·속도·피격: `scripts/game/RunnerStage.gd`
- 보스 진행: `scripts/game/BossStage.gd`
- 플레이어 무기·피격: `scripts/player/PlayerController.gd`
- 보스 파츠 모션: `scripts/boss/RobotSamuraiBoss.gd`
- 설정: 원본 SettingsPopup 및 사용자 설정 저장 코드

원본과 웹판의 구현 방식이 다를 때는 오브젝트 개수 자체보다 화면에서 보이는 타이밍, 강도, 상태 전환 결과를 우선 일치시킨다.

## 3. 범위 결정

- `COMBO` 이미지와 숫자 이미지를 사용하는 중앙 콤보 임팩트 팝업
- 러너 및 보스 콤보 증가 시 동일한 팝업 호출
- Fever 속도선, 무지개 버스트, 시작 플래시, 강화된 `TAP!!` 펄스
- Fever 중 배경·지형 2배 이동, 오브젝트 2배 이동, 플레이어 달리기 3배 재생
- 공격 성공·실패·Fever 시작의 짧은 히트스톱과 화면 충격
- 피격 중 월드 감속, 입력 잠금, 8단계 데미지 플래시
- 실제 플레이에서 `errorSfx` 재생
- 지원 브라우저에서 공격·피격 진동과 설정 저장
- 칼집 리소스와 칼/칼집 상태 전환 기반 구현
- 플레이어 발밑 그림자
- 보스 천 조각, 배경 회전, 파츠별 동작, 피격·패배 연출
- 보스 Fever에도 공통 Fever 오버레이 적용
- 러너/보스 HUD 모드 구분
- HOW TO에 `COMBO & FEVER` 안내 추가
- 연출을 재현할 수 있는 자동 테스트와 시각 QA 경로

### 3.2 명시적 제외 및 보류

다음 항목은 알려진 상태로 유지한다.

1. **Sword Debug 패널**
   - 기본 펼침 상태를 유지한다.
   - 우측 280px을 가리는 현재 배치를 유지한다.
   - `swordDebugAlwaysVisible = true`와 칼 상시 표시를 유지한다.
   - 디버그 종료 후 사용자가 별도로 삭제를 요청할 때 제거한다.

2. **`BOSS FEVER!`가 즉시 `HIT`으로 덮이는 문제**
   - 이번 구현에서는 메시지 호출 순서나 표시 큐를 수정하지 않는다.
   - 보스 Fever 오버레이까지 구현한 뒤 사용자가 실제 플레이를 확인하고 별도 수정을 요청할 때 처리한다.
   - 따라서 이번 완료 판정에서 `BOSS FEVER!` 문구의 지속 노출은 요구하지 않는다.

3. **원본에서도 사용하지 않는 리소스**
   - `slash_effect.png`는 원본 런타임에서도 연결되지 않아 필수 패리티 항목으로 넣지 않는다.
   - `footstep_grass_000.ogg`는 원본 테스트가 발소리 미재생을 의도적으로 확인하므로 게임에 추가하지 않는다.
   - `sky_static.png`는 흰색 매트 문제 때문에 현재 그라디언트 대체를 유지한다.

4. **신규 아트 제작과 적 캐릭터 교체**
   - 이번 작업은 기존 원본 연출 복구가 목적이므로 신규 적·배경 제작은 포함하지 않는다.

### 4.1 리소스 원칙

- 원본 파일은 `public/assets/godot-source/assets/` 아래에서 수정하지 않는다.
- 투명도 보정이 필요하면 로드 후 파생 텍스처를 생성하되 원본 파일은 보존한다.
- `BootScene` 키 이름은 실제 소비 모듈과 1:1로 맞춘다.
- 로드만 하고 소비하지 않는 키는 완료 단계에서 다시 목록화한다.
- 브라우저가 OGG를 재생하지 못하는 경우를 확인하되, 원본 대체 파일 생성은 실제 호환성 문제가 확인된 후 결정한다.

## 5. 목표 구조

`GameScene.ts`는 전체 상태 전환과 게임 규칙을 조정하고, 세부 연출은 다음 모듈로 분리한다.

```text
src/game/
├─ effects/
│  ├─ ComboImpactPopup.ts       # COMBO 이미지와 숫자 팝업
│  ├─ FeverImpactOverlay.ts     # 속도선·버스트·플래시
│  └─ HitFeedbackController.ts  # 히트스톱·화면 충격·피격 플래시
├─ entities/
│  ├─ PlayerVisualController.ts # 달리기·칼·칼집·피격 상태
│  └─ BossVisualController.ts   # 보스 파츠와 상태별 모션
├─ services/
│  └─ GameSettings.ts           # 볼륨·진동 설정과 localStorage
├─ scenes/
│  ├─ BootScene.ts
│  └─ GameScene.ts
└─ rules.ts
```

구현 중 실제 파일명은 저장소 관례에 맞춰 조정할 수 있지만, 다음 책임 분리는 유지한다.

- 게임 규칙과 연출 수치를 섞지 않는다.
- 프레임마다 임시 Phaser 오브젝트를 만들지 않는다.
- 씬 전환 시 모든 Tween, Timer, Graphics, Audio 참조를 정리한다.
- 러너와 보스가 공통으로 쓰는 콤보·Fever·피격 연출을 중복 구현하지 않는다.

## 6. 세부 구현 계획

### EP-10. 콤보 임팩트 팝업

#### 원본 기준

- `COMBO` 이미지 표시 크기: 500×375
- 각 숫자 이미지 표시 크기: 250×250
- 시작 배율: 0.4
- 재생 시간: 0.35초
- 0.4에서 1.0까지 cubic-in으로 확대 후 숨김
- 화면 중앙 정렬
- 러너와 보스 모두 콤보가 증가할 때 재생

#### 구현

1. `BootScene`에서 `num0`부터 `num9`까지 로드한다.
2. `ComboImpactPopup`이 `combo.png`와 필요한 자릿수 이미지만 조합한다.
3. `play(combo: number)` 호출 시 이전 Tween을 취소하고 0.4 배율부터 다시 시작한다.
4. 한 자리, 두 자리, 세 자리 이상에서도 숫자 묶음의 중심이 화면 중앙에 오도록 계산한다.
5. 매 호출마다 이미지를 새로 만들지 않고 최대 자릿수 풀을 재사용한다.
6. 러너 `successObject()`와 보스 `successBossPattern()`의 콤보 증가 직후 호출한다.
7. Fever 중 원본 규칙상 콤보가 증가하지 않는 경로에서는 팝업도 호출하지 않는다.

#### 완료 조건

- 러너와 보스에서 `COMBO` 글씨와 실제 콤보 숫자가 함께 보인다.
- 0.35초 재생 후 완전히 숨고 입력을 막지 않는다.
- 빠른 연속 성공에서도 이전 숫자나 Tween이 남지 않는다.
- 화면 크기가 바뀌어도 논리 화면 중앙을 유지한다.

### EP-20. Fever 화면 오버레이

#### 원본 기준

- 속도선 100개
- 선 굵기 25~45, 길이 300~1180
- 이동 속도 2200~5200
- 알파값 변화와 무지개 Fever 색상
- 버스트 풀 8개, 버스트마다 광선 12개
- 버스트 생성 간격 0.08~0.18초, 지속 0.24~0.42초
- Fever 시작 플래시 0.12초

#### 구현

1. `FeverImpactOverlay`에 속도선 상태 100개를 미리 만들고 `Graphics`에 묶어 그린다.
2. 버스트는 8개 풀을 재사용하고 각 버스트가 12개의 방사형 광선을 그리게 한다.
3. `start()`, `update(delta)`, `stop()`, `destroy()` 생명주기를 제공한다.
4. `start()`에서 0.12초 전면 플래시를 실행하고 속도선·버스트를 활성화한다.
5. `stop()`에서 화면을 즉시 정리하고 남은 Timer/Tween을 취소한다.
6. 현재 단색 청록 사각형은 보조 색조로만 남기거나 원본 대비에 맞춰 강도를 낮춘다.
7. 러너 Fever와 보스 Fever가 같은 인스턴스 규격을 사용한다.
8. `TAP!!`은 원본에 가까운 1.0 → 1.26 → 0.96 펄스를 반복하도록 바꾼다.

#### 완료 조건

- Fever 시작 순간 플래시, 속도선, 버스트가 동시에 체감된다.
- 종료 즉시 모든 Fever 전용 요소가 사라진다.
- 러너와 보스에서 동일한 오버레이 품질을 유지한다.
- 반복 진입 후 Graphics, Tween, Timer 개수가 계속 증가하지 않는다.

### EP-21. Fever 속도와 진행감

#### 구현

1. 배경·지형 공통 이동 배율을 `feverActive ? 2.0 : 1.0`으로 통합한다.
2. 현재 구현된 오브젝트 속도 420 → 840 전환은 유지하되 공통 배율 함수에서 관리한다.
3. 달리기 애니메이션은 Fever 중 기본 12 FPS의 3배 속도로 재생한다.
4. Fever 시작 시 일반 오브젝트를 정리하고 Fever 전용 러시 스폰을 시작한다.
5. Fever 종료 시 러시 스폰을 중단하고 남은 전용 오브젝트를 정리한 뒤 정상 스폰 복구 구간으로 전환한다.
6. Fever 시작 시 0.08초 히트스톱과 강도 7의 충격을 적용한다.

#### 완료 조건

- 오브젝트만 빨라지는 것이 아니라 배경, 지형, 캐릭터 달리기가 함께 가속된다.
- Fever 종료 후 모든 속도가 정확히 기본값으로 돌아온다.
- 재시작, 보스 전환, 메뉴 이동 후 Fever 배율이 남지 않는다.

### EP-30. 히트스톱과 피격 피드백

#### 원본 기준

| 상황 | 히트스톱 | 충격 강도 |
| --- | ---: | ---: |
| 적 처리 성공 | 0.05초 | 4 |
| 공격 실패/피격 | 0.04초 | 5 |
| 수집 대상 오공격 | 0.04초 | 3 |
| Fever 시작 | 0.08초 | 7 |

피격 상태는 0.4초 동안 유지되며, 이때 배경 이동은 0.1배, 오브젝트 이동은 0배가 되고 플레이어 입력이 잠긴다. 플레이어는 빨강/흰색 계열의 8단계 플래시를 표시한다.

#### 구현

1. `HitFeedbackController`가 월드 업데이트 배율과 UI/연출 업데이트를 분리한다.
2. 히트스톱 중 월드 이동만 멈추고 콤보 팝업·Fever 오버레이·HUD 정리는 계속 실행한다.
3. 피격 0.4초 동안 입력을 잠그고 배경 0.1배, 오브젝트 0배를 적용한다.
4. 데미지 스프라이트와 Tint/Alpha Tween으로 8단계 플래시를 구현한다.
5. 상태가 중간에 종료되거나 씬이 바뀌어도 Tint, Alpha, 배율을 기본값으로 복원한다.
6. 기존 카메라 흔들기는 원본 충격 강도와 함께 조정하고 중복 진동으로 과해지지 않게 한다.

#### 완료 조건

- 성공 공격과 실패 공격의 손맛이 시각적으로 구분된다.
- 피격 중 오브젝트가 플레이어를 지나쳐 연속 피해를 만들지 않는다.
- 피격 종료 후 입력, 이동, 색상, 투명도가 정상 복구된다.

### EP-31. 효과음, 진동, 설정

#### 구현

1. 러너 피격과 보스 패턴 실패에서 `errorSfx`를 재생한다.
2. 공격 시 35ms, 피격 시 140ms 진동을 기본값으로 적용한다.
3. `navigator.vibrate` 지원 여부를 확인하고 미지원 환경에서는 오류 없이 무시한다.
4. 설정 화면의 `AUDIO 100%`를 실제 볼륨 조절 컨트롤로 바꾼다.
5. `ATTACK VIBRATION`, `HURT VIBRATION`을 각각 토글 가능하게 만든다.
6. 볼륨과 진동 설정을 `localStorage`에 저장하고 다음 실행 시 복원한다.
7. 음악과 효과음의 최종 볼륨은 마스터 볼륨과 각 사운드 기본 볼륨을 곱해 계산한다.
8. 브라우저 오디오 정책에 따라 최초 사용자 입력 이후 재생을 시작하는 현재 흐름을 보존한다.

#### 완료 조건

- `errorSfx`가 실패 상황에서 한 번만 들린다.
- 설정 변경이 현재 재생 중인 음악과 이후 효과음에 즉시 반영된다.
- 새로고침 후 설정이 유지된다.
- 진동 미지원 브라우저와 데스크톱에서도 콘솔 오류가 없다.

### EP-40. 플레이어 무기와 상태 연출

#### 구현

1. `sword_sheath.png`를 로드하고 플레이어의 별도 칼집 레이어로 배치한다.
2. 정상 게임 상태의 기본 규칙은 다음처럼 만든다.
   - 평상시: 칼집 표시, 베기 칼 숨김
   - 공격 활성 0.12초: 칼집 숨김, 베기 칼 표시
3. 현재 Sword Debug의 상시 표시가 켜져 있으면 디버그 설정이 위 규칙보다 우선해 베기 칼을 계속 표시한다.
4. 따라서 이번 작업 중에는 현재 디버그 화면과 칼 표시가 달라지지 않지만, 나중에 디버그를 제거하거나 상시 표시를 끄면 칼집 전환이 즉시 동작한다.
5. 플레이어 발밑에 92×18, Alpha 0.34의 타원형 그림자를 추가한다.
6. `playerIdle`은 원본의 실제 런타임 상태 전환 호출을 다시 추적한 뒤 필요한 정지 구간에만 연결한다.
7. 무기 위치·크기는 현재 Sword Debug 값과 같은 좌표 공급원을 사용해 이후 조정값이 칼과 칼집에 일관되게 반영되도록 한다.

#### 완료 조건

- Sword Debug 기본 펼침과 칼 상시 표시는 현재와 동일하다.
- 디버그 상시 표시를 끈 검증 경로에서는 평상시 칼집, 공격 시 칼 전환이 동작한다.
- 공격 중 칼과 칼집이 의도치 않게 동시에 겹치지 않는다.
- 그림자는 캐릭터와 함께 보이되 베기·피격 스프라이트보다 아래에 위치한다.

### EP-50. 보스 배경과 파츠 모션

#### 구현

1. 보스 배경을 회전 중 모서리가 노출되지 않는 크기로 확장하고 초당 0.05라디안으로 회전시킨다.
2. `bossClothLeft`, `bossClothRight`를 보스 컨테이너의 실제 파츠로 추가한다.
3. `BossVisualController`에 다음 상태를 구현한다.
   - `idle`: 호흡, 머리 상하 움직임, 천 흔들림
   - `windup`: 현재 요구 패턴에 맞춘 공격 준비
   - `strike`: 팔·검의 빠른 타격
   - `recover`: 기본 자세 복귀
   - `stun/hit`: 피격 흔들림과 코어 반응
   - `defeated`: 파츠 정지, 붕괴 및 잔해 연출
4. 기존 전체 컨테이너의 단순 상하 움직임은 위 상태 모션 안으로 흡수한다.
5. 보스 공격 패턴 판정과 시각 모션의 시작·활성·회복 타이밍을 같은 상태 데이터에서 관리한다.
6. 보스 Fever 시작 시 공통 `FeverImpactOverlay`를 활성화한다.
7. 보스전 실패 시 플레이어 피격 피드백과 `errorSfx`를 적용한다.
8. `BOSS FEVER!` 문구가 `HIT`으로 덮이는 현재 호출 순서는 변경하지 않는다.

#### 완료 조건

- 보스 천 파츠가 보이고 idle/attack/hit 상태에 따라 자연스럽게 움직인다.
- 회전 배경의 빈 모서리가 1280×720과 844×390 화면에서 보이지 않는다.
- 패턴 판정과 보스 공격 모션이 시각적으로 어긋나지 않는다.
- 보스 Fever에서 속도선·버스트·플래시가 보인다.

### EP-60. HUD와 HOW TO 패리티

#### HUD

1. 러너 모드에서는 점수, HP, 콤보, 코인, Fever 게이지를 표시한다.
2. 보스 모드에서는 러너 콤보/코인/Fever 채움을 숨기거나 초기화하고 보스 HP와 패턴/Fever 남은 시간을 우선 표시한다.
3. 보스 콤보 증가는 HUD 숫자가 아니라 공통 콤보 임팩트 팝업으로 전달한다.
4. 모드 전환 직후 이전 모드의 값이나 Tween이 남지 않게 한다.

#### HOW TO

1. 기존 네 개 안내에 다섯 번째 `COMBO & FEVER` 카드를 추가한다.
2. 카드에 성공 연속 처리, Fever 게이지, Fever 중 속도 증가와 공격 판정 확대를 설명한다.
3. 1280×720 안에서 카드가 잘리지 않도록 가로 캐러셀이나 드래그/화살표 이동을 제공한다.
4. 모바일 터치와 키보드 모두로 안내 카드를 이동할 수 있게 한다.

#### 완료 조건

- 러너와 보스 HUD 정보가 섞이지 않는다.
- HOW TO에서 다섯 번째 카드에 접근할 수 있고 뒤로 가기 동작이 유지된다.

## 8. 테스트 계획

### 8.1 단위 테스트

- 콤보 자릿수 분해와 이미지 키 매핑
- 콤보 연속 호출 시 마지막 값 우선 처리
- Fever/피격/히트스톱 월드 속도 배율
- Fever 시작·종료 상태 초기화
- 보스 모션 상태 전환 순서
- 볼륨 계산, 진동 설정, `localStorage` 직렬화
- 진동 API 미지원 환경의 no-op 처리

### 8.2 통합 테스트

- 러너 성공 → 콤보 증가 → 팝업 재생
- Fever 100 → 오버레이/가속/러시 스폰 → 정상 종료
- 공격 실패 → 콤보 초기화 → 월드 감속 → `errorSfx` → 복구
- 러너 종료 → 보스 전환 시 러너 전용 오버레이와 Timer 제거
- 보스 성공 → 콤보 팝업과 보스 피격 모션
- 보스 Fever → 공통 Fever 오버레이 활성화
- 재시작/메뉴 이동 후 Tint, 속도, 오디오, Tween 잔존 여부

### 8.3 E2E 및 시각 QA

테스트에서 시간이나 랜덤 스폰을 기다리지 않도록 개발/테스트 환경 전용 트리거를 둔다. 프로덕션 UI에는 노출하지 않는다.

- 콤보 1, 9, 10, 99 캡처
- 러너 Fever 시작/진행/종료 캡처
- 피격 플래시 중간 프레임 캡처
- 보스 idle/strike/hit/Fever 캡처
- 1280×720 데스크톱 확인
- 844×390 모바일 가로 확인
- 390×844 세로 방향 안내 회귀 확인
- 각 시나리오의 브라우저 콘솔 오류 확인

Godot 원본과 비교할 때는 같은 이벤트 발생 시점을 기준으로 다음을 대조한다.

1. 연출 시작 지연
2. 전체 지속 시간
3. 화면 내 중심과 크기
4. 이동 속도와 흔들림 강도
5. 종료 후 남는 오브젝트 유무

### 8.4 성능 및 누수

- 속도선과 버스트는 풀링하며 프레임 루프에서 Phaser 오브젝트를 새로 생성하지 않는다.
- Fever 10회 반복 후 GameObject, Tween, Timer 수가 계속 증가하지 않아야 한다.
- 기준 테스트 환경에서 Fever 중 프레임 시간 p95가 20ms 안쪽을 목표로 한다.
- 저사양 모바일에서 지속적인 프레임 저하가 확인되면 선 수를 임의로 줄이기 전에 Graphics 배치와 갱신 빈도를 먼저 최적화한다.

### 8.5 실행 명령

```text
npm test
npm run build
npm run test:e2e
```

시각 회귀 스크립트를 추가할 경우 `npm run test:visual`로 통일하고 CI 또는 로컬 QA에서 같은 해상도를 사용한다.

## 12. 구현 착수 원칙

이 문서 승인 후에는 단계 0부터 순서대로 진행한다. 원본과 다른 연출을 새로 해석해 추가하기보다, 먼저 원본 수치와 상태 전환을 복구한다. 각 단계 완료 시 실제 화면과 자동 테스트 결과를 함께 확인하고, 사용자 확인이 필요한 보류 이슈는 기존 동작을 유지한 채 별도로 보고한다.
